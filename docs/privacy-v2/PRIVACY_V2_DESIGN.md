# Akmena PrivacyEngine v2 — Design

## Problem with v1

The v1 `PrivacyEngine` (`src/privacy/PrivacyEngine.sol`) is a hash-commitment
scheme **without zero-knowledge proofs**:

- `depositPrivateEscrow(bytes32 commitment)` records `commitment`.
- `executePrivateSettlement(nullifierHash, secret, amount, stealthRecipient)`
  reveals the **full preimage** on-chain and checks
  `keccak256(nullifierHash, secret, amount, stealthRecipient) == commitment`.

**Consequence:** anyone observing the settlement transaction recomputes the
commitment and locates the exact deposit. Unlinkability = 0. The "pool" is a
delayed public transfer with extra steps. (This matches the research brief's
§6.2: "you keep the accounting properties and lose *all* the privacy properties.")

Additional v1 flaws:
1. **Variable amounts** — deposit amount ≈ withdrawal amount uniquely identifies
   the depositor (amount correlation). No denominations.
2. **No relayer mechanism** — the settler pays gas from their own address,
   creating an on-chain link.
3. **Mempool theft** — the preimage *is* the authorization; anyone copying it
   from the mempool could settle first (recipient is committed, so theft is
   limited to griefing, but the secret has zero confidentiality).
4. **Native-only** — agents settle in ERC-20s (USDC), not just ETH.
5. **No agent integration** — disconnected from intents, operators, policy.

## v2 Architecture

A **fixed-denomination ZK private pool** (Tornado Cash / Privacy Pools / RAIL20
architecture, adapted for agent commerce):

```
DEPOSIT (public)                    WITHDRAW (private)
─────────────                    ──────────────────
agent picks (nullifier, secret)    agent picks recipient, relayer, fee
  off-chain, random 31 bytes         off-chain
         │                                    │
         ▼                                    ▼
commitment = Poseidon(nullifier,   proof = Groth16{
  secret)                              nullifier, secret, merklePath;
                                       public: root, nullifierHash,
                                       recipient, relayer, fee
                                     }
         │                                    │
         ▼                                    ▼
  pool.deposit(commitment)            pool.withdraw(proof, ...)
  value == DENOMINATION                 │
                                        ▼
                                 contract checks:
                                   root known, nullifier unspent,
                                   verifyProof(...) == true
                                        │
                                        ▼
                                 nullifier marked spent;
                                 DENOMINATION - fee → recipient
                                 fee → relayer
```

### On-chain footprint

| Action | Revealed | Hidden |
|--------|----------|--------|
| Deposit | commitment, depositor, timestamp, denomination | nullifier, secret |
| Withdraw | nullifierHash, root, recipient, relayer, fee | **which deposit**, nullifier, secret |

### Primitives

1. **Commitment:** `Poseidon(nullifier, secret)` — hiding + binding, SNARK-friendly.
2. **Accumulator:** incremental Merkle tree, depth 20 (~1M leaves), Poseidon hashes.
   Contract stores current root + 100-root history (proofs survive block delays).
3. **Nullifier:** `Poseidon(nullifier)` published at spend; `mapping` prevents
   double-spend without revealing the source commitment.
4. **Circuit** (`circuits/withdraw.circom`, 5,313 constraints): proves
   (a) commitment membership via Merkle path, (b) nullifier derivation,
   (c) binds recipient/relayer/fee as public signals.
5. **Verifier:** Groth16 over BN254, auto-generated by snarkjs (~220–250k gas).
6. **Denominations:** one pool contract per denomination (e.g. 0.1 / 1 / 10 ETH).
   Anonymity set = deposits in the pool.
7. **Relayers:** fee bound in the proof; relayer cannot redirect or overcharge.

### Trust assumptions

- **Trusted setup:** Groth16 requires a per-circuit ceremony. The included
  `withdraw_final.zkey` was generated with a **local single-contributor
  ceremony — TEST ONLY**. Production needs a multi-party MPC (or reuse the
  perpetual Powers of Tau + a proper phase-2 ceremony).
- **Anonymity set:** privacy scales with deposits. A pool with 3 deposits gives
  ~1.5 bits of anonymity. Documented via `anonymitySetSize()`.
- **Timing correlation:** deposit → immediate withdraw is linkable by timing.
  Users (agents) should observe a random delay. Not enforceable on-chain.
- **Relayer knowledge:** the relayer learns (recipient, fee, timing) but NOT
  the depositor. Documented, not ignored.

### What v2 does NOT do (explicit non-goals)

- **Amount confidentiality beyond denominations** — variable amounts need range
  proofs (v3).
- **Recipient unlinkability** — combine with stealth addresses (EIP-5564):
  withdraw to a fresh stealth address. The registry already exists in-repo.
- **ERC-20 pools** — the circuit is asset-agnostic; an ERC-20 pool variant is
  a straightforward extension (deposit via `transferFrom`, withdraw via `transfer`).
- **Viewing keys / association sets** — specified as extensions (Railgun PPOI /
  0xbow ASP model), not implemented in v2.
- **Policy integration** — the pool composes with `AkmenaPolicyBoundary` at
  deposit (policy-checked funding) and withdrawal (to authorized targets);
  the shielded interior is unobserved. Enforcement points are deployment
  configuration, not in-pool logic (Protocol Rule #1: layers stay separate).

## Files

- `circuits/withdraw.circom` — the ZK circuit
- `circuits/build/` — compiled artifacts (r1cs, wasm, zkey, ptau)
- `contracts/AkmenaPrivatePool.sol` — the pool
- `contracts/WithdrawVerifier.sol` — snarkjs-generated Groth16 verifier
- `contracts/PoseidonT3.sol` — Poseidon library (must match circuit hash)

## Verification

`test/PrivatePoolV2.t.js` (Node + snarkjs) and `test/AkmenaPrivatePool.t.sol`
(Foundry) cover:
1. Deposit → generate proof → withdraw succeeds; recipient gets denomination - fee.
2. Double-spend (same nullifier) reverts.
3. Tampered proof (wrong recipient) fails verification.
4. Unknown root reverts.
5. Wrong denomination deposit reverts.
6. Fee > denomination reverts.
7. On-chain tree root matches circuit-computed root (Poseidon consistency).
